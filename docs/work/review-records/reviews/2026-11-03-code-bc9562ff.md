FINDINGS (most severe first)

1. R. scripts/spec_gate.py:200-217 (`edges_of_move`), reached via 250-258 (`record_problem`) and 261-276 (`merged_items_problem`). A correct merge is refused: merging main into a branch whose HEAD never touched the work item.
   - Scenario A, reproduced. Main has the item at draft. A branch is cut. Main then locks it with a fresh record, moves it to building, and refines functional.md. FR-13 allows that refinement. Running `git merge --no-ff main` on the branch gives: `spec-gate: docs/work/demo/README.md: record is stale (reviewed 4a08bdbd, committing e728dd33)`. The merge is not committed.
   - Scenario B, reproduced. The same happens when the item does not exist in the branch HEAD at all.
   - Scenario C, same code path (not run). A diverged `git pull` that merges origin/main hits it too, and so does a `--no-ff` merge of a feature branch that refined its spec after the lock into a draft or absent main.
   - Cause: for a merge, import or squash, FR-10 judges the chain from HEAD status (or draft) to the staged status. It demands a design record fresh for the merged content, even though the merged item tree is exactly MERGE_HEAD's, which already passed the gate on its own history. The record can never be fresh once the spec was refined during the build, so the only ways out are a pointless re-review or `--no-verify`. Shipped items on main have the same effect, needing design and code fresh.
   - The gate will run on every commit in every repo, and "update my branch from main" is routine in a worktree fleet.
   - Gap category: new: gate false positive on merge of already-gated history. Class: design. Spec text FR-10 and AC-8 require this literally, so the spec needs amending. AC-8 never tests a merge whose item side came wholly from one parent.
   - A fix to consider: skip the edges when the merged item tree (all hashed files) equals MERGE_HEAD's or HEAD's. Keep the chain for the conflict, both-sides-moved and squash cases, which have no MERGE_HEAD.
