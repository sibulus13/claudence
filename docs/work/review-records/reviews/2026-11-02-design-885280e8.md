## R findings

**R1. FR-8 code binding can wrongly allow a ship and wrongly refuse one.** components.md:50, D29. Category: new `proxy-for-tree` (a commit-message citation stands in for "the code is unchanged"). Class: design. The authoritative source for "code changed after review" is the tree diff between the reviewed commit and what is being committed. The spec instead uses `git log` for Spec-trailer citations.

Wrongly allowed:
- (a) On a non-default branch, source commits need no Spec trailer (spec_gate.py:169). Merge conclusions return None before any trailer check (spec_gate.py:165-166). So fix commits made after the review carry no citation. The log scan finds nothing and the ship passes with unreviewed code.
- (b) The ship commit can itself stage source edits, and nothing diffs the index against the reviewed commit. The scan covers only HEAD's history, not the staged change.
- (c) A commit that changes this item's code but cites another item's trailer passes.

Wrongly refused:
- (d) A squash or rebase merge makes the reviewed sha a non-ancestor of HEAD. The usual flow is: review on the feature branch, squash-merge, then ship. The record is refused with no remedy except a re-review. During a merge or squash commit, HEAD is the first parent, so the reviewed commit sits on the other side.
- (e) The commit that adds the `reviews/*.md` record often carries a `Spec:` trailer. It then voids its own record. Docs-only or README commits that cite the item do the same.

No AC covers any of these. AC-7 has only one "later commit stages source" fixture.

Fix: require no source-file diff (using the gate's SOURCE and NOT_SOURCE patterns) between `commit` and the index. State what happens when the commit is not an ancestor, for example resolve it through the tree.

## F findings

- **F1.** FR-8 and FR-9: a `fix-first` record that is newer for the same content can be deleted in the lock or ship commit itself, and the older `pass` then wins. A cheap detector fails safe: refuse deletion of any `reviews/*.md` present at HEAD. The rejection of "records deleted after the move" does not cover this.
- **F2.** FR-8: "latest `recorded` decides" has no tie-break. It is UTC ISO at an unstated precision. Two records in one second tie, and machine clock skew breaks the order. Specify precision and a deterministic tie-break, for example by name.
- **F3.** NFR-1 and AC-12: `IndexTree.read` runs one `git show` per file, 20 files plus `ls-files`. On Windows that is probably around 1 s, so the test may flake. Suspicion, not measured. A single `cat-file --batch` fixes it.
- **F4.** FR-2 needs file modes (120000 symlink, 160000 gitlink). The `Tree` interface has only names (spec_check.py:74-128), and the spec says only "add a `files` listing". State the mode API. DiskTree is listed as a wrap target but is not used.
- **F5.** `research` and `experiment` items ship on a design record that must equal the final hash. Research READMEs accumulate results, so the lock-time review is always stale at ship. A "design" re-review of results is the only way through. State it, or accept it.
- **F6.** AC-5, AC-7 and AC-8 pass or refuse without asserting the reason string. A refusal for the wrong reason (for example a hash error) would pass AC-8.
- **F7.** A renamed item folder inside the pattern (e.g. a `git mv` of a locked item) is allowed by FR-12 and brings stale records. This is consistent with the inventory, but nothing tests it.
