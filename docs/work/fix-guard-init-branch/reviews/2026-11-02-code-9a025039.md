R1. `hooks/guard.py` `init_targets`, the `-C` branch (`where = resolve_dir(where, rest[1])`, about line 295). **Blocks.**
- Unrelated git commands are now denied. `-C` is resolved before the subcommand is checked, so any `git -C <value>` whose value has `$`, `%`, `~`, `-` or is empty raises `Unresolvable`. `check_shell` turns that into a deny.
- From cwd `D:/repo/Lib/telefi`, old guard allows and new guard denies with "Cannot tell where this git init/clone would create a repo":
  - `for d in */; do git -C "$d" pull; done`
  - `git -C "$(pwd)" status`
  - `git -C $DIR log --oneline`
  - `git -C ${REPO} diff`
  - `git status; git -C $x log`
  - PowerShell `git -C $env:USERPROFILE status`
  - `git -C ~ status`
  - `git -C - status`
  - `git -C "" status`
  - `git -C %CD% status`
  - Also `cd $X && git -C sub status`, because `where` is `None` there.
- The message tells the agent to use a literal absolute path for a command that is not an init or clone. `git -C <var>` is very common in agent loops.
- Fix at the source: on `Unresolvable` from `-C`, set `where = None` and raise only if the subcommand turns out to be `init` or `clone`. The existing `where is None` check already does the raising. Add a regression test with `git -C "$d" status` expecting allow.
- Gap: false-denial of non-target commands (the spec's "Unchanged" scope). Class: implementation, with a test gap. No AC covers `-C` with a variable value on a non-init subcommand.
