1. should-fix (build amendment) | C:/Users/Michael/.claude/scripts/projects_sweep.py:194-196 (git_run) | rating F | breaking: no | class C
   git_run uses text=True with no encoding, so stdin and stdout use the locale code page (cp1252 here,
   sys.flags.utf8_mode=0, no PYTHONUTF8 in the scheduled wrapper). Git for Windows reads/writes paths as UTF-8.
   Probe (temp repos, real commit_moves, a tracked n/<name> moved to archive/<name>):
     - 'café.md'  -> ["git-add-failed: fatal: pathspec 'archive/caf?.md' did not match any files"], nothing committed
     - '日本.md'   -> UnicodeEncodeError raised from nul_list->stdin encode, nothing committed (same shape as the
                      2026-11-15 incident: moves sit uncommitted, exit non-zero)
     - 'a[1].md'  -> [] clean (glob chars are fine: a literal match wins)
   With PYTHONUTF8=1 all three commit cleanly, so `encoding="utf-8"` on the subprocess.run in git_run closes it.
   Before the fix the same names "worked" partially (args go through UTF-16; ls-files quoting hid the tracked
   source, so the destination was committed and the source deletion silently left as " D"), so this is a change of
   failure mode from silent-partial to loud-total, not a new data loss. Reachability C: 0 non-ASCII paths exist in
   the fleet docs repo today and no log shows one; effect is a loud failure. The item's risk list does not name
   encoding at all although the stdin channel is exactly what introduces it.
   Closing rule: git_run passes encoding="utf-8"; add a negative fixture (one non-ASCII tracked file moved) to the
   AC-1 test or a sibling row.
   Gap category: new: subprocess-text-encoding (class implementation).
